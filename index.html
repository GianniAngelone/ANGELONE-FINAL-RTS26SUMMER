Hardware Security – Tamper Detection System

A FreeRTOS-based ESP32-S3 system that treats a button as a tamper sensor. A short interrupt signals two bottom-half tasks that measure wake-up latency and log the security event under both idle and loaded conditions.

Project Overview

This project implements a hardware-security oriented interrupt system on the ESP32-S3 using FreeRTOS. A push-button on GPIO 18 is treated as a tamper sensor. When the button is pressed, a fast interrupt service routine (the top-half) runs immediately. The ISR performs only the minimum work required: debouncing the input, recording the entry timestamp, pulsing a diagnostic GPIO, and signaling two bottom-half tasks.

The two bottom-half tasks are responsible for the slower work. One task is woken by a binary semaphore; the other is woken by a direct task notification. Both tasks calculate the latency from the moment the ISR started until the task began running, then log the result. This design follows the classic top-half / bottom-half pattern used in real embedded and operating-system kernels.

The system can be run in two modes. In idle mode only the interrupt path and the two bottom-half tasks exist. In loaded mode, four additional background tasks (carried forward from an earlier assignment) run on the same core and create realistic scheduling contention. Comparing the two modes shows how higher-priority work affects interrupt response time.

The project is relevant to embedded firmware, security, and safety-critical roles. The same pattern appears in secure boot monitors, industrial emergency stops, and any system that must react quickly to an external event while keeping the interrupt handler itself very short.

Task Priority Type Role

load_b 10 Periodic (20 ms) Background load
load_c 5 Periodic (50 ms) Background load
load_d 2 Periodic (100 ms) Background load

The two bottom-half tasks only exist to respond to the tamper interrupt. The four load tasks are enabled only when WITH_LOAD = 1 and are used to create contention on Core 1.

Timing Evidence (Latency Measurements)

Because this is an event-driven interrupt system rather than a set of periodic tasks, the key timing metric is interrupt-to-task latency (the time from ISR entry until the bottom-half task starts running).

Idle conditions (WITH_LOAD = 0)

  • Direct notification max latency: 30 µs
  • Binary semaphore max latency: 2309 µs

Loaded conditions (WITH_LOAD = 1)

  • Direct notification max latency: 17 706 µs
  • Binary semaphore max latency: 10 369 µs

Under load the notification path became approximately 590× slower and the semaphore path became approximately 4.5× slower. The main cause is load_a running at priority 15, which is higher than the bottom-half tasks (priority 12).

Hazard Analysis

Delayed Response

A higher-priority task (load_a) can run after the ISR and delay the bottom-half tasks, increasing latency.

Lost Events

A binary semaphore does not count. Multiple presses that occur while the bottom-half is still running can be lost.

Missing Yield

If portYIELD_FROM_ISR is omitted, the woken bottom-half task may not run until the next natural scheduling point.

Final Reflection

Going into Real-Time Systems, I already had experience with programming and embedded systems, but I mostly thought about software in terms of whether it worked or not. This class changed that way of thinking.

Looking Back

I learned that in a real-time system, when something happens can be just as important as what happens. A system can produce the correct result and still have a problem if the response takes too long.

That became much more obvious to me while working on my final project. I built a tamper detection system where a button on the ESP32-S3 triggers an interrupt. The interrupt then wakes two different bottom-half tasks.

What Was Harder Than Expected

The hardest part of the class for me was getting the systems to behave consistently. A lot of the problems were not simple programming mistakes. I had issues with task scheduling, interrupts, task priorities, stack sizes, communication between tasks, and simulator behavior.

My final project was a good example of this. I eventually ran into FreeRTOS crashes related to task notifications. I had to stop changing random pieces of code and understand what the system was actually doing. I learned that task notifications depend on valid task handles and that initialization and task ownership matter in a concurrent system.

What I Would Do Differently

If I did the project again, I would spend more time planning the task structure before writing the code. I tended to start coding and then fix problems as they appeared.

I would also test smaller pieces of the system before combining everything together. For example, I would verify the interrupt first, then the semaphore path, then the notification path, and finally add the background load.

I would also spend more time testing on actual hardware. Wokwi was extremely useful, but a simulator does not behave exactly like a physical ESP32-S3.

Most Valuable Thing I Learned

The most valuable thing I learned is to think about an embedded program as a system of activities competing for time and resources, instead of just a list of instructions.

Before this class, I would mostly ask, "Does this work?" Now I am more likely to ask what has the highest priority, what happens if two things occur at the same time, how long a task can be delayed, and what happens when the system is under load.

What I Will Take Into Future Work

I am interested in embedded and computer engineering, so I expect these ideas to come up again in projects involving microcontrollers, robotics, automation, and other hardware systems.

The biggest change for me is that I no longer think of timing as something considered only after the program is finished. I see timing, scheduling, and concurrency as part of the design itself.

Overall, this class gave me a better understanding of what is happening underneath embedded software and gave me more confidence when debugging systems that do not behave the way I expect.

The biggest lesson I am taking away is simple: correctness is not only about getting the right answer. In a real-time system, it is also about getting that answer at the right time.

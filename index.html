Hardware Security – Tamper Detection System

A FreeRTOS-based ESP32-S3 system that treats a button as a tamper sensor. A short interrupt signals two bottom-half tasks that measure wake-up latency and log the security event under both idle and loaded conditions.

Project Overview

This project implements a hardware-security oriented interrupt system on the ESP32-S3 using FreeRTOS. A push-button on GPIO 18 is treated as a tamper sensor. When the button is pressed, a fast interrupt service routine (the top-half) runs immediately. The ISR performs only the minimum work required: debouncing the input, recording the entry timestamp, pulsing a diagnostic GPIO, and signaling two bottom-half tasks.

The two bottom-half tasks are responsible for the slower work. One task is woken by a binary semaphore; the other is woken by a direct task notification. Both tasks calculate the latency from the moment the ISR started until the task began running, then log the result. This design follows the classic top-half / bottom-half pattern used in real embedded and operating-system kernels.

The system can be run in two modes. In idle mode only the interrupt path and the two bottom-half tasks exist. In loaded mode, four additional background tasks (carried forward from an earlier assignment) run on the same core and create realistic scheduling contention. Comparing the two modes shows how higher-priority work affects interrupt response time.

The project is relevant to embedded firmware, security, and safety-critical roles. The same pattern appears in secure boot monitors, industrial emergency stops, and any system that must react quickly to an external event while keeping the interrupt handler itself very short.

Task Table

Task Priority Type Role
btn_sem 12 Event-driven Bottom-half using binary semaphore
btn_notif 12 Event-driven Bottom-half using direct notification
load_a 15 Periodic (10 ms) Background load – highest priority
load_b 10 Periodic (20 ms) Background load
load_c 5 Periodic (50 ms) Background load
load_d 2 Periodic (100 ms) Background load

The two bottom-half tasks only exist to respond to the tamper interrupt. The four load tasks are enabled only when WITH_LOAD = 1 and are used to create contention on Core 1.

Timing Evidence (Latency Measurements)

Because this is an event-driven interrupt system rather than a set of periodic tasks, the key timing metric is interrupt-to-task latency (the time from ISR entry until the bottom-half task starts running).

Idle conditions (WITH_LOAD = 0)

  • Direct notification max latency: 30 µs
  • Binary semaphore max latency: 2309 µs

Loaded conditions (WITH_LOAD = 1)

  • Direct notification max latency: 17 706 µs
  • Binary semaphore max latency: 10 369 µs

Under load the notification path became approximately 590× slower and the semaphore path became approximately 4.5× slower. The main cause is load_a running at priority 15, which is higher than the bottom-half tasks (priority 12).

Hazard Analysis

Delayed Response

A higher-priority task (load_a) can run after the ISR and delay the bottom-half tasks, increasing latency.

Lost Events

A binary semaphore does not count. Multiple presses that occur while the bottom-half is still running can be lost.

Missing Yield

If portYIELD_FROM_ISR is omitted, the woken bottom-half task may not run until the next natural scheduling point.
